# 覆盖维度与需求类型清单

用于会前覆盖扫描和收口前查漏。逐项标“清楚 / 部分 / 缺失 / 不适用”。只把“部分”和“缺失”且会改变结果的项变成问题；“不适用”要写一句理由，防止误判。不必在会上逐条念，挑影响最大的问。

## 通用维度

| 维度 | 要能回答的问题 |
| --- | --- |
| 目标与价值 | 解决谁的什么问题？不做的代价？成功指标及观察方法？非目标是什么？ |
| 角色与权限 | 有哪些角色（含管理员、外部用户、系统账号）？谁能看、谁能改、谁能批？前端可见和服务端授权是否一致？ |
| 组织与租户差异 | 不同组织/客户/地区/业务线的规则是否不同？差异是配置还是代码？ |
| 核心流程 | 端到端主路径的入口、步骤、终点；跨角色交接点 |
| 业务规则 | 计算、校验、优先级、分配、状态流转规则；每条有正反例 |
| 数据与生命周期 | 关键对象有哪些字段/状态？创建、修改、撤销、删除、归档、历史数据如何处理？ |
| 边界与例外 | 空数据、单条、上限、重复、并发、过期、撤回 |
| 失败与恢复 | 部分成功、超时、重复提交、外部系统不可用时用户看到什么、怎么补救 |
| 集成与依赖 | 依赖哪些接口/系统/团队？契约是否已存在？谁负责缺口？ |
| 通知与反馈 | 谁在什么时候被通知？渠道？失败时如何处理？ |
| 报表与审计 | 需要统计什么？操作是否需要留痕、可追溯、可导出？ |
| 非功能 | 性能（量级、响应时间，写单位和测法）、安全与合规、隐私、可用性、兼容（浏览器/设备）、无障碍、多语言/时区 |
| 上线与运营 | 灰度/切换方式、新旧并行期、回滚方案、培训与文档、监控与告警、上线后谁负责 |
| 验收 | 谁验收？用什么数据和场景？通过标准是什么？ |

## 按需求类型补充的必问项

**旧系统重构 / 迁移**
- “和旧版一样”具体指哪一部分：行为、界面、数据、URL/入口、还是性能？哪些旧行为其实是 bug 或绕路，不该照搬？
- 新旧并行期多长？期间数据如何同步、以谁为准？
- 旧数据、旧链接、书签、外部系统回调如何兼容？
- 旧系统里有哪些按组织、按账号、按邮箱写死的特殊逻辑？是否全部保留？
- 用什么方式证明新旧一致（对比口径、抽样数据）？

**全新功能**
- 现在用户靠什么方式完成这件事（Excel、微信、人工）？新功能要替代哪一步？
- 最小可用版本是什么？哪一步缺了就整条流程走不通？
- 冷启动：初始数据从哪来？

**系统集成 / 对接**
- 数据流向、触发方式（推/拉/定时）、频率、量级
- 字段映射与主数据归属：冲突时以谁为准？
- 对方不可用、返回错误、数据延迟时的业务处理
- 联调环境、测试账号、对方的排期与对接人

**流程 / 制度变更**
- 谁的工作方式会改变？是否需要审批、培训、过渡期？
- 进行中的单据按旧流程还是新流程走完？
- 例外审批的出口在哪？

**数据 / 报表类**
- 指标的精确定义（分子、分母、时间口径、去重规则、时区）
- 数据来源和刷新频率；与现有报表对不上时以谁为准
- 谁能看哪些维度的数据

## 常见的隐藏矛盾

收口前快速对一遍：

- 一条“所有人都能 X”与另一条“某角色不能 X”
- “实时”与依赖的批处理/定时同步
- “和旧版一样”与“顺便优化一下”
- “首版简单做”与“必须支持所有组织的特殊规则”
- 前端隐藏 vs 服务端放行（或反之）
- 删除需求 vs 审计/报表需要历史数据
- 不同参会人对同一术语的不同理解
